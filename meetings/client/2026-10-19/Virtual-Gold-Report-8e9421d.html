Today I’ll give a short update on the redaction service and the new privacy components.

The service handles the steps before and after a cloud AI call: it replaces private text with placeholders, then restores those placeholders in the reply when requested.

The main change is that several privacy components now have real implementations connected to the service.

Three workflow APIs, plus policy, health, and monitoring endpoints.

POST/v1/redactions

Send: purpose + structured email, including body, headers, and quoted thread.

Receive: redacted text, request ID, span decisions, and degraded status.

02 / AFTER THE CLOUD REPLY

Restore the reply

POST/v1/redactions/{rid}/restore

Send: reply_text using the original request ID.

Receive: RESTORED + restored text, or BLOCKED + reason.

03 / AFTER USE

Delete the record

DELETE/v1/redactions/{rid}

Action: remove the request record and its retained mapping before expiry.

Receive: 204, including unknown IDs. Repeated deletion does not extend deletion-marker retention.

To enable restoration: set mapping.retain: true on the original redaction request. Retention is off by default; records expire at their TTL.

Presenter notes · request fields, response rules, and integration limits

This page shows what the client’s system can call.

First, it sends the task and email to the redaction API. The service returns the redacted content, a request ID, and information about what was changed. The client’s system then makes the cloud AI call.

Second, after the reply comes back, the client can use the restore API with the same request ID. To enable this, the first request must set mapping.retain to true. It is off by default. If the reply contains an unknown placeholder, restoration is blocked rather than guessed.

Third, the delete API removes the request record and its saved mapping. Session labels can remain until they expire, so labels stay consistent across requests.

The other endpoints show the active policy, check service and model status, and provide monitoring data.

One important point: if processing fails, the client should not forward the input. If the service reports a degraded result, it used a fallback, and the client decides whether to send that result onward.

Presenter notes · components, provisional policy, and implementation limits

The new privacy work improves three parts of the service.

First, detection. Rules now find money amounts, phone extensions, client-listed terms, and names taken from the email headers. Presidio adds another way to find private information. When detections overlap, the service combines them and keeps the more sensitive category. The latest fix also keeps the required redaction flags for client-listed terms, even when the model gives a low score.

Second, policy and scoring. The updated policy adds demographic information, network identifiers, and money amounts. These categories still need client review. The code can adjust model scores using labelled examples, but that step is not fitted yet. For now, it leaves the scores unchanged. The client term list is also still empty.

Third, person labels. When the identity is clear, “Dana Whitfield,” “Dana,” and “Whitfield” can share one placeholder. Restoration uses the full name. If a shared name such as “Dana” becomes unclear across requests, it gets a separate label instead of being linked to the wrong person. Session state now stores protected fingerprints of the values instead of the original text. The mapping needed to restore a reply is kept separately.

These components use the existing API interfaces. We can also switch back to the original test components for development.

Anmol’s presenter notes · prototype and dataset

I’ll now cover the model workstream.

We built a prototype that finds possible private text, asks the model to judge it in context, and uses code to decide what to mask. It also saves the decisions, response times, and failure reasons so we can inspect each email.

The dataset contains 100 fictional business emails and 999 labelled spans. Of these, 971 require masking. We split the emails into 60 for development and 40 reserved for the final test.

We improved name detection using headers, greetings, and sign-offs. We also added patterns for colleague mentions and health information, and made health, organization, and code-name categories explicit in the prompt.

This is the model prototype. Connecting it to the service and VG08 is a separate step, so these results do not mean the deployed service is complete.

Anmol’s presenter notes · results, measures, and comparison limits

This table compares the same 15 development email IDs. The 70B run used a hosted API. The 8B and Qwen figures are earlier local M4 results, and they still need a fresh run with the same updated pipeline.

The 70B run found about 93 percent of the labelled entities. It also found all 67 labelled name mentions in this sample. But about 16 percent of the labelled private characters remained visible. That is still a meaningful amount of private text.

There is a trade-off: 70B masked more public text, about 18 percent, compared with about 10 percent for 8B and 6 percent for Qwen.

The recorded median was about 41 seconds per email. We should not read that as a model-size speed advantage: the machines and pipeline versions were different. It also does not tell us the speed of a future private-cloud setup.

The 70B run had one fallback because the API reached its credit limit. These 15 emails cover only four of the dataset’s 15 business domains. We need more validation before making broader claims.

Anmol’s presenter notes · deployment, other models, and next steps

Our enterprise recommendation is Llama 3.3 70B on infrastructure controlled by the client. For laptop use, the fallback is Llama 3.1 8B through local Ollama. The laptop results leave more private text visible, so that trade-off needs to be clear.

The hosted benchmark does not prove that raw email stays inside the client’s environment. We still need to verify the chosen endpoints, logs, telemetry, and outbound network behavior in the private deployment.

Gemma 2 27B also looks promising in a three-email pilot, but its full 15-email attempt hit credit limits in every case. We cannot use that attempt to rank the model’s quality.

Next, we’ll compare the updated models under the same settings, validate score adjustment on fresh examples, and use the remaining 45 development emails to address misses. That includes organizations, identifiers, health text, and incomplete confidential facts.

We also need to agree acceptable leakage, public masking, speed, and failure behavior with the client. After freezing the pipeline, we’ll run the reserved 40-email test once and report it separately from development results.
