A · 使用情境:貴方問了什麼、我們檢視了什麼、我們提議什麼

10 分
1 · 貴方 9/15 問的
專案該做垂直的金融服務情境,還是做能為任何產業淨化敏感資料的橫向應用?Inderpal 提了一個具體的垂直:公開申報文件與市場資料上的交易助理,交易員的策略留在本地。貴方請我們回來給方向。
2 · 我們檢視的:垂直線,用一個情境看
小型資產管理公司的交易員問:「根據 Apple 最新的 10-Q,服務營收趨勢對我目前的部位有什麼影響?」閘道因為碰到持倉而標為機密。本地 8B 模型先答;財務表格讓信心偏低,需要升級。送到雲端的只有公開的部分:「摘要 Apple 最新 10-Q 的服務營收趨勢」。她的持倉、策略筆記、身分都不出去。雲端的摘要與本地算的曝險在裝置上合併。每一步都有紀錄。這是垂直,因為資料格式、「機密」的定義、benchmark 都是交易專屬的。
3 · 我們檢視的:橫向線,用一個情境看
任何公司的 IT 部門已經在用雲端模型做客服回覆、合約摘要、內部問答。同一個閘道坐在他們和 API 之間:客訴信出去時人名、帳號、電話換成佔位符,回來時還原;法務備忘錄出去時組織與金額被替換;標為機密的人資文件直接拒絕。三個部門、一個濾網、不需要懂業務。換產業只改 recognizer 清單。這是橫向,因為閘道可以單獨量測:偵測率、洩漏率、還原成功率。
4 · 我們發現的:「兩條線」和「只做垂直」差在哪
差別不在系統怎麼跑,在閘道是助理裡面的一個零件,還是一個獨立的元件。只做垂直:閘道是交易助理內部的程式,只認股票代號、持倉、策略筆記,只在交易情境測,成績只出現在助理的數字裡。兩條線:閘道做成獨立元件,助理是它的第一個使用者。具體來說,「都做」多了四件事:
只做垂直兩條線
介面助理內部的函式獨立的介面:任何程式丟文字進去,拿回淨化後的文字和一張對照表。助理呼叫它,別的應用也能呼叫它
規則寫死:代號、持倉、策略筆記設定檔:哪些實體要抓、哪些來源算機密、每種欄位怎麼處理。換產業改設定,程式不變
測試資料只有交易情境加上非金融的文件:客服工單、合約、人資紀錄。證明換領域一樣抓得到
指標只在助理的表裡閘道自己一張表:逐類別偵測率、洩漏率、還原成功率、多輪洩漏,與助理答案對不對無關
運作上沒有差:交易員問問題,持倉留本地,公開部分上雲,兩種做法跑起來一模一樣。多花的大約是一到兩成的工,幾乎都在閘道那邊(多包一層介面、規則抽成設定檔、多一批測試資料)。為什麼值得:貴方 9/15 問「橫向」,其實是在問這個閘道能不能拿去別的地方用。只做垂直的答案是「理論上可以,沒試過」;兩條線的答案是「可以,這是它在三個領域的成績單」。
5 · 我們的提議
兩條線都做,以 Inderpal 提的交易助理為垂直。為什麼選這個垂直:貴方提的;所有輸入資料都公開且免費(SEC EDGAR 申報文件、市場行情、MIT 授權的 FinQA 當可評分的 benchmark);本地與雲端的切分有交易員一看就懂的商業理由:策略是祕密,申報文件不是。兩條線各做什麼,見下面三張表。

模型與推論:研究簡報
MVP 的選擇與理由
Llama 3.1 8B Instruct 為主模型,Qwen3 8B 為獨立對照;Hugging Face transformers 在程式內執行;bitsandbytes 4-bit NF4;T4 上用 FP16 計算。程式內執行是因為信心實驗需要原始 logits、逐 token 分數與 hidden states,推論 API 不提供。用 FP16 不用 BF16:T4 是 compute capability 7.5,先前假設 BF16 是錯的,已修正。第一輪比較只用一種量化路徑;不要在同一個實驗混用 NF4、GPTQ、AWQ。
16 GB 的 T4 放得下什麼
Llama 3.1 8B 的 KV cache 在 FP16 下約每 token 128 KB,32K token 的上下文一條序列約 4 GB,還沒算 activation 和抓下來的 hidden states。名義上的 128K 上下文在 T4 上不是實用的 128K。先用預設的 dynamic cache;量化或 offload 的 cache 只在量到記憶體問題時才試。
更新的模型:追蹤,不直接替換
Qwen3.5-9B(多模態、混合架構)要先做 hidden states 與記憶體的 smoke test 才可能取代 Qwen3 8B。Qwen3.8-27B 在 T4 上放不下(4-bit 光權重就約 13.5 GB)。Llama 4 Scout 的報告是單張 H100,對 T4 沒有參考價值。任何候選模型都要過同一套產物、硬體、介面、品質的關卡才能進 MVP。
信心路徑,與 harness 設計一致
從原始 logits 取選定 token 的對數機率當基準線(平均、低尾、低於門檻的比例、答案長度);k=5 的多樣本語意一致性是第一個延伸;語意熵探針在 held-out 資料上掃一小組層,不寫死層數。門檻在 dev 資料上選;報告準確率對升級率,不是一個放諸四海的門檻。
每次執行都要記的
模型與 tokenizer 版本、函式庫版本、GPU、量化與 dtype、輸入輸出 token 數、首 token 時間、每秒解碼 token 數、p50 與 p95 延遲、記憶體峰值、batch 大小與 cache 策略。廠商的 token/s 數字不進客戶報告。期中基準線關掉 speculative decoding。
兩件要決定的
Llama 授權:Meta 的社群授權有署名要求和每月 7 億使用者的條款,商用部署前要法務審閱。Jev(託管的型別化決策服務)只提議在核准的非機密資料上做獨立比較;它不提供 logprob 與 hidden states,又多一個合約邊界,所以不在本地信心基準線裡。
信心調度與機密性閘門:兩個元件怎麼互動(設計草稿)
一條原則
機密性閘門是硬約束;信心分數只在閘門允許的空間內調度。兩者不合併成一個數字,也不能互相替代。信心回答「需不需要升級」;閘門回答「能不能升級」。
閘門無條件先跑
每個請求先查一次敏感度標籤,O(1) 的查表,不牽涉模型。信心再高也不能跳過閘門,因為信心會被分布外或對抗性輸入誤導。閘門輸出三檔:可上雲;淨化後上雲;只能本地。
然後信心在該檔內調度
可上雲:本地先答,組合分數低於門檻才升級,門檻依敏感等級乘任務類型分別校準。淨化後上雲:同上,但只有淨化後的部分出去。只能本地:分數不再決定要不要升級,只決定用哪種本地兜底,成本遞增:多樣本自我一致性、更大的本地模型、本地檢索、明說不確定的回答、人工複核佇列。
從安全研究採納的修正
只看敏感度的閘門是 MINIM 消融裡表現最差的政策(任務必要內容只留 4%)。草稿因此加入從使用者問題推導的任務必要性分數,三檔由敏感度與必要性共同決定。兩個分數都在檢索前算,來自來源與問題,所以評分層不在 prompt injection 的攻擊面內。
另外併入的三條約束
什麼能出去在檢索前決定,申報文件裡植入的文字無法放寬;授權是確定性的白名單程式碼,不是模型的判斷;揭露量以會話為單位預算,列為開放風險而非承諾,因為兩種預算法都給不出可證明的上界。
稽核
每個請求的閘門判定都留紀錄,包括本地回答的;敏感等級也控制完整 prompt 能不能進日誌與遙測,不只控制能不能出去。
未解
必要性評分模組還只是原則,沒有設計;會話預算未解;任何必須出現在最終回答裡的欄位要用可逆的轉換,設計階段就定;被回顧的方法都沒在金融資料上驗證過;閘門加信心的組合還沒在原型裡整合。
