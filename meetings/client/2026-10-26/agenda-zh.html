03偵測：規則和 Presidio

Yudi10/25

先用資料測固定格式的偵測器，修最嚴重的錯，再測一次。需要看上下文的情況（拆開的地址、公司還是人名、商業機密、健康資訊）交給模型，不手寫規則。

怎麼測的

  • 資料集：ai4privacy pii-masking-400k，1,000 筆英文驗證資料（合成，美國和英國）。只放在本機，授權不允許再散布。
  • 它的 17 個標籤有 16 個對得到我們的類別。只評分表裡交給規則或 Presidio 的類別。
  • 標註項目只要和任何偵測到的片段重疊，就算抓到。

04分級表提案（policy 0.1.3）

請客戶審：Q1Yudi

22 個類別，4 個 tier。Yudi 提出這一版，因為在測試資料上比較準。改動已經準備好，客戶確認後就合併。完整的表也在附件（tier-table-client-review-en.docx）。

和目前版本（0.1.1）的差別

  • BANK_ACCOUNT → ACCOUNT_NUMBER：現在涵蓋銀行、券商和客戶帳號、IBAN、加密錢包和其他長串數字 ID。
  • 新增 ADDRESS_PUBLIC（Public）：公開的辦公室和公司地址，不再被當成住家地址。
  • Public 門檻 0.5 → 0.8：看起來公開的項目，要模型相當確定是隱私才遮。公開的聯絡方式本來就是要給人的，風險在於把個人電話誤當成公開電話。

各 tier 怎麼處理

本地模型給每個項目一個分數，也就是它是隱私的機率。tier 決定門檻。

Tier規則什麼時候遮每個請求可調整
High遮分數 ≥ 0.2，模型不太確定也遮否
Medium遮分數 ≥ 0.5是，呼叫的應用可以自訂門檻
Low保留，除非組合出現同一欄出現 3 種以上不同的 Low 類別（例如城市 + 雇主 + 年齡）否
Public確定公開就保留分數 ≥ 0.8否

不論分數一律遮：客戶的機密詞清單、請求標為禁止的字詞、模型無法分類的項目。所有門檻都是起始值，之後用測試集調。

類別

Tier類別
HighGOV_ID、CREDENTIAL、CARD_NUMBER、ACCOUNT_NUMBER、HEALTH、BUSINESS_CONFIDENTIAL、CODENAME、DEMOGRAPHIC
MediumPERSON、PHONE_PERSONAL、EMAIL_PERSONAL、ADDRESS_HOME、NETWORK_ID、AMOUNT
LowCITY、DATE、ORG、AGE、GENDER

個人資料的 tier 依照 NIST SP 800-122 的影響等級；健康和人口特徵依 GDPR 第 9 條列為 High。商業類別和 Public tier 是我們的提案，請客戶對照他們的資料分級確認。

06測試集：100 封信，1,054 個標註項目

Karinabaseline v1.1

還是原本那 100 封虛構的主管信件，重新整理成服務可以直接評分的格式。這也回答了 Aarvin 在期中問的「LLM 產生的標註怎麼能信」：標註由 LLM 提出，再由人逐筆檢查。

改了什麼

  • 每封信都是一個服務請求。可以直接送進 API；每個項目帶有服務自己的欄位位置、類別和 tier，結果不用轉換就能評分。
  • 每個項目標成遮或保留。共 1,054 個：1,006 個要遮、48 個保留。984 個和第一版一致，15 個改成保留（例如 no-reply@ 信箱、公司公開的辦公室地址），新增 55 個（大多是機密事實裡的人名和金額）。
  • 照目前的分級表（policy 0.1.1）標註。如果客戶確認 0.1.3，再更新類別。
  • 切分：60 封用來開發，40 封保留給最後一次測試。

初步分數

07加密提案：對話金鑰，兩種模式

聽客戶看法：Q6Zhexuan

和現行 API 並存的第二版（v2）。兩種模式都已實作並放進服務，預設關閉，現行 API 不受影響。變成預設之前，想先聽客戶的看法。

mapping · 預設

參照 token + 加密對照表

  • token 指向伺服器上的紀錄；原文先加密再存
  • 刪掉某個 group 的對照表，它的 token 就失效
  • 需要持久儲存對照表和金鑰
aes_siv · 替代方案

token 就是加密後的原文

  • 伺服器不存原文對照表
  • 同一段對話裡，相同的值和類別得到相同的 token
  • token 隨原文變長；模型必須原封不動傳回

流程

  1. 遮蔽。客戶的應用送出文字和自己的對話 ID（group_id）。第一個請求為這段對話產生隨機金鑰，之後的請求沿用。
  2. Agent。Agent 把遮蔽後的訊息原樣往下傳，不碰金鑰。
  3. 還原。把文字送回來。每個 token 會指出它屬於哪段對話；服務檢查權限和期限後還原。
  4. 關閉。對話結束時用同一個 ID 關閉，它的 token 就不能再還原。

金鑰保護

每段對話有自己的隨機金鑰，由主金鑰封裝；不同用途各自衍生金鑰。呼叫端拿不到金鑰。對話預設最長 24 小時。多個服務實例透過 Redis 共用狀態。

Placeholder 長什麼樣子

現行 APIv2 提案
Placeholder[PERSON_1]，短，看得出類別[VG:2:…]，比較長，隨原文變長
還原需要request ID只要文字
保存的狀態每個請求每段對話，最長 24 小時
用真實模型測過有，在模型評測裡還沒

v2 接下來

  • 測真實模型會不會原封不動保留長 token。
  • 修一個會把部分一般的方括號文字誤判成 token 的檢查。
  • 技術文件在 repo 的 docs/api/，需要的話可以給客戶一份。
