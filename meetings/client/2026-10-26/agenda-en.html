03Detection: rules and Presidio

YudiOct 25

We tested the fixed-format detectors on data, fixed the worst errors, and tested again. Context cases (loose address parts, company versus person, business secrets, health) are left to the model rather than hand-written rules.

How we tested

  • Dataset: ai4privacy pii-masking-400k, 1,000 English validation rows (synthetic, US and UK). Kept on our machines; its licence bars redistribution.
  • 16 of its 17 labels map to our categories. Only types the tier table assigns to rules or Presidio are scored.
  • A labelled item counts as found if any detected span overlaps it.

04Proposed tier table (policy 0.1.3)

for your review: Q1Yudi

22 categories in 4 tiers. Yudi proposes this revision because it matched the test data more accurately. The changes are ready and will be merged once you confirm. The full table is also in the attached document (tier-table-client-review-en.docx).

Changes from the current table (0.1.1)

  • BANK_ACCOUNT → ACCOUNT_NUMBER: now covers bank, brokerage and client accounts, IBANs, crypto wallets and other long numeric IDs.
  • New ADDRESS_PUBLIC (Public): published office and business addresses, so they are not treated as home addresses.
  • Public threshold 0.5 → 0.8: a public-looking item is redacted only when the model is fairly sure it is private. Public contacts are meant to be shared; the risk is a personal number mistaken for a public one.

How each tier is handled

The local model gives each item a score: the probability that it is private. The tier sets the cut-off.

TierRuleRedacted whenAdjustable per request
HighRedactScore ≥ 0.2, even when the model is fairly unsureNo
MediumRedactScore ≥ 0.5Yes, the calling app may set its own threshold
LowKeep, unless combined3 or more different Low categories in the same field (e.g. city + employer + age)No
PublicKeep if confidently publicScore ≥ 0.8No

Always redacted, whatever the score: your term list, words a request marks as forbidden, and items the model cannot classify. All thresholds are starting values, tuned later on the test set.

06Test set: 100 emails, 1,054 labelled items

Karinabaseline v1.1

The same 100 fictional executive emails as before, rebuilt so the service can be scored on them directly. This also answers Aarvin's question at the midterm about how we can trust labels an LLM produced: an LLM proposed the labels, and a person checks every one.

What changed

  • Each email is a service request. It goes straight into the API, and each item carries the service's own field positions, category and tier, so results score with no conversion.
  • Every item is marked redact or keep. 1,054 items: 1,006 to redact, 48 to keep. 984 agree with the first version, 15 moved to keep (e.g. no-reply@ mailboxes, the company's public office address), and 55 were added (mostly names and amounts inside confidential facts).
  • Labelled against the current tier table (policy 0.1.1). If you confirm 0.1.3, we update the categories.
  • Split: 60 emails for development, 40 held back for one final test.

Rules catch every email address and 79% of names, but no bank accounts, code names, health details or ID numbers. The model has to close that gap.

What the test set tells us about the tier table

  • 86 items that should be redacted sit in the Low tier: 67 company names, 12 cities, 6 dates, 1 age. Because a Low item seen alone is kept, the service would let all 86 through, even when the model is sure they are private. The worst are deal counterparties and dates of birth.
  • 39 ID numbers (case, medical record and order numbers) have no category yet. They are redacted by default, so nothing leaks, but public ones like filing numbers get over-masked.
  • Only 4 of the 100 emails are fully clean; the other 96 contain something to redact.

07Encryption proposal: conversation keys, two modes

for your view: Q6Zhexuan

A second version of the API (v2) alongside the current one. Both modes are implemented and in the service, switched off by default. The current API is unchanged. We would like your view before we make it the default.

mapping · default

Reference token + encrypted mapping

  • The token points to a server-side record; the original is encrypted before it is stored
  • Deleting a group's mappings invalidates its tokens
  • Needs persistent storage for mappings and keys
aes_siv · alternative

The token is the encrypted original

  • No original-value mapping is stored on the server
  • Same value and type in one conversation give the same token
  • Tokens grow with the length of the original; models must pass them through exactly

How it works

  1. Redact. Your app sends the text with its own conversation ID (group_id). The first request creates a random key for that conversation; later requests reuse it.
  2. Agent. Agents pass the redacted message on unchanged. They never handle keys.
  3. Restore. Send the text back. Each token tells the service which conversation it belongs to; the service checks permissions and expiry, then restores.
  4. Close. When the conversation ends, close it with the same ID. Its tokens can no longer be restored.

Key protection

Each conversation has its own random key, wrapped by a master key; separate keys are derived for each purpose. Callers never receive keys. A conversation lives up to 24 hours by default. Service copies share state through Redis.
