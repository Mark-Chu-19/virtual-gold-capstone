1Restore design: a key the server issues

before Nov 2A18B73ZhexuanAnmol

API v2 (PR #10, on main and switched off) expects the client to send its own conversation ID, group_id. Aarvin asked for the reverse: the server creates the identifier and returns it. Anmol agreed to draw the flow and email it. Zhexuan owns the code, so the diagram and the code have to describe the same design.

Side by side

API v2 todayWhat Aarvin asked for
Who creates the IDThe client (group_id)The server, on the first redaction
What the client sends to redactText + group_idThe text only
What it gets backRedacted textRedacted text + the key ID
RestoreThe text only; each token names its conversationThe text + the key ID
Placeholder[VG:2:…], grows with the original"Encrypted output" (not specified further)

What we need to settle

a. One key per conversation, or per request?

The notes say both: "one hash key per conversation and request". With one key per request, a multi-turn conversation gets a new key each turn, and the agent cannot restore text that mixes tokens from two turns. With one key per conversation, the client has to send the key ID back on the second redaction so the server reuses it.

b. Which mode?

"Encrypted output replacing placeholders" sounds like aes_siv: no stored mapping, a longer token. Whether a cloud model returns long tokens intact is still untested. Anmol's demo on Monday showed the short [PERSON_1] form from his prototype, not the v2 token.

c. Fix the token check before real use

B73: the v2 token check (wire.py lines 11 and 14) treats ordinary text such as [VGA] or [Item_1] as a token and rejects it. It has to be fixed before the client's agent sends real traffic.

RecommendationOne key per conversation. The server creates it on the first redaction and returns its ID; the client sends the ID back on later redactions in the same conversation and on restore. This keeps most of v2: only who creates the ID changes. Zhexuan and Anmol agree the flow today; Anmol emails the diagram to Aarvin by Wednesday and asks him to confirm per conversation or per request.
