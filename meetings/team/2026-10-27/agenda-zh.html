要決定的事

a. 每個對話一把金鑰，還是每個請求一把？

紀錄裡兩個都寫了：「每個對話與請求一把 hash key」。如果每個請求一把，多輪對話每一輪都換一把，agent 就無法還原混了兩輪 token 的文字。如果每個對話一把，客戶第二次遮蔽時要把金鑰 ID 送回來，伺服器才能沿用。

b. 用哪種模式？

「用加密後的輸出取代 placeholder」聽起來是 aes_siv：不存對照表，token 比較長。雲端模型會不會把長 token 原封不動傳回來，還沒測過。Anmol 週一的 demo 用的是他原型裡的短格式 [PERSON_1]，不是 v2 的 token。

c. 正式使用前先修 token 檢查

B73：v2 的 token 檢查（wire.py 第 11、14 行）會把 [VGA]、[Item_1] 這類一般文字當成 token 擋掉。客戶的 agent 開始送真實流量前一定要修好。

建議每個對話一把金鑰。伺服器在第一次遮蔽時建立並回傳 ID；同一對話之後的遮蔽與還原，客戶都把 ID 送回來。這樣 v2 大部分保留，只改「誰產生 ID」。今天 Zhexuan 和 Anmol 先對齊流程；Anmol 週三前把流程圖 email 給 Aarvin，請他確認是每個對話還是每個請求。
