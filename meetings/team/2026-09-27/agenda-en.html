3What happens when confidence lands in the middle

Zhexuan ↔ Yudi · 20 min

Depends on items 1 and 2 — you need the categories and the ground truth before you know what "the middle" looks like.

WhoAnswer
YudiUse thresholds, err toward caution (High tier drops to 0.2)

On this emailHarborview — a project code name (sensitive) or a place name (not)? The model returns 0.55.

Yudi: above the Medium threshold of 0.5 → mask
Karina: detected, so mask
Zhexuan: between auto-redact and reject → PENDING_REVIEW

Under Zhexuan's design the executive hits "draft me a reply" and gets back "still processing", then waits for a person to go and decide what Harborview is.
Why this is a conflict, not just a preferenceYudi states "without per-item human review" as this project's research contribution — on the grounds that Rescriber, the closest prior system, requires the user to confirm every item, and we cannot.

What Zhexuan added is exactly that mechanism. The two contribution claims cancel out.
The observation that resolves itHuman review exists because getting it wrong is expensive.

Karina's entire argument is that getting it wrong is cheap, because everything is restored. If that argument holds, the reason for human review disappears.
SuggestionTake "mask anyway, and log the low-confidence spans for later analysis".

It does three things at once: keeps Yudi's contribution claim, matches Karina's reversibility, and does not require a reviewer who does not exist.

And Zhexuan's PENDING_REVIEW need not be thrown away — keep it in the API, disabled in v0, as a future option. Leaving the interface in place also reads well to the client.

Decide: what happens in the middle band. If human review stays, we must also answer who the reviewer is.

Proposed · one threshold plus logging; PENDING_REVIEW stays in the spec, off in v0 Concretely:
1. Drop the threshold pair (auto-redact / reject); keep one.
2. Below the threshold, mask anyway — masking is reversible, so the cost of being wrong is already small — but tag it low_confidence and log it.
3. That log is the over-masking measurement. Karina's metric set already includes over-mask rate; this gives it a data source instead of needing a second mechanism.
4. Keep PENDING_REVIEW in the API decision enum but never return it in v0. The interface stays, so if the client later does want human review, the contract does not change.

Why this satisfies all three: Yudi's "without per-item human review" contribution claim survives; Karina's reversibility argument is exactly what justifies it; Zhexuan's mechanism is not discarded, only deferred.

If the meeting decides to keep human review, it must answer "who reviews" in the same breath — one executive, dozens of times a day. Without an answer we cannot present this design to the client.

The first two are the same thing under two names — rename and move on, five minutes. The third is new and needs a real discussion.

On this emailDana Whitfield becomes PERSON_1 this time. Three days later another email mentions Dana —

session mapping: does not remember (new session, new numbering)
global context store: remembers, and shares it across all callers

If the CEO's assistant and the CFO's assistant share one context store, does a lookup on Dana from the CFO side return what was recorded on the CEO side?
Why it needs a real discussionZhexuan's API document says the global context store "holds known private information persistently" and is "shared across all callers and sessions".

That makes it a higher-value target than the vault (it is never cleared), and it sits in direct tension with the same document's own principle that sensitive content is never logged. Encryption, retention and access control are not specified.

Decide: (a) one name for the first three. (b) whether the global context store exists at all; if it does, who protects it, and whether cross-caller sharing is intended.

Proposed · call it the vault; drop the context store from v0 (a) Naming: the first two become vault (Karina's word, the most descriptive, and unambiguously session-scoped). session mapping and "mapping table" stop being separate components. Five minutes, then move on.

(b) The global context store: proposed not to build it in v0. Four reasons:
1. It is the highest-value target in the system — it holds private information persistently and, unlike the vault, is never cleared.
2. Encryption, retention and access control are entirely unspecified, and specifying them takes time we do not have this week.
3. Cross-caller sharing is a privacy problem nobody asked for — an entity labelled on the CEO's side becoming visible on the CFO's side is not requested anywhere in the client material.
4. The core flow does not need it — without it every request still detects, masks and restores correctly; what is lost is a cross-session memory optimisation.

Proposed: move it to a later phase as a standalone optimisation with its own security design. Dropping it now is cheap and adding it back later is easy; carrying it now makes it a liability in every security conversation from here on.
