Zhexuan ↔ Yudi · 20 分

依賴第 1、2 項(要先知道類別和標準答案,才知道中間區間長什麼樣)。

Zhexuan:落在自動遮蔽與拒絕門檻之間 → PENDING_REVIEW

在 Zhexuan 的設計下,主管按下「幫我擬回覆」之後,拿到的是「還在處理中」,然後要等一個人去看 Harborview 是什麼。
為什麼這是衝突,不只是選項差異Yudi 把「不需要逐項人工審查」明確寫成本專案的研究貢獻 — 理由是最接近的前人系統 Rescriber 需要使用者確認每一項,而我們不能。

Zhexuan 加進來的正是那個機制。兩人的貢獻主張會互相抵銷。
關鍵觀察人工審查存在的前提是「遮錯了代價很大」。

而 Karina 整個提案的論點就是「遮錯了代價很小」— 因為會還原回來。如果那個論點成立,人工審查的動機就消失了。
建議選「一律遮蔽 + 記錄低信心 span 供事後分析」。

同時做到三件事:保住 Yudi 的貢獻主張、符合 Karina 的可還原性、不需要一個現實中不存在的審查員。

而 Zhexuan 的 PENDING_REVIEW 不必丟掉 — 寫進 API 但 v0 不啟用,降級成未來選配。介面先留著,對客戶也有說服力。

要決:低信心區間的處置。若保留人工審查,必須同時回答「審查員是誰」。

建議方案 · 單一門檻 + 記錄,PENDING_REVIEW 留在規格但 v0 不啟用 具體做法:
① 不要雙門檻(auto-redact / reject),只留一個。
② 低於門檻的 照樣遮 — 因為可還原,遮錯的代價本來就小 — 但標記為 low_confidence 記錄下來。
③ 那批記錄就是過度遮蔽的量測資料。Karina 的指標裡本來就有 over-mask rate,這樣它有了資料來源,而不是另外再做一套。
④ PENDING_REVIEW 保留在 API 的 decision enum 裡,但 v0 永遠不回傳。介面先留著,之後客戶若真的要人工審查,不用改契約。

為什麼這樣同時滿足三方:Yudi 的「不需要逐項人工審查」貢獻主張保住了;Karina 的可還原性論點正是這個做法的依據;Zhexuan 的機制沒有被丟掉,只是延後啟用。

如果會議決定保留人工審查,那必須當場回答「審查員是誰」 — 一位主管每天用幾十次,這題沒有答案的話,這個設計就不能對客戶講。

建議方案 · 統一叫 vault;context store 從 v0 拿掉 (a) 命名:前兩列統一叫 vault(Karina 的名字,最貼切,而且範圍明確是單一 session)。session mapping 和「對照表」不再當成獨立元件。五分鐘決定,不要花時間。

(b) global context store:建議 v0 不做。四個理由:
① 它是整個系統最高價值的攻擊目標 — 持久保存私密資訊,而且不像 vault 會清除。
② 加密、保留期限、存取控制目前完全沒有規格,補齊要時間。
③ 跨呼叫端共用是個沒有人要求的隱私問題 — CEO 助理標記過的實體,CFO 助理查得到,這件事沒有任何一份文件說客戶要。

建議移到後期,當成獨立的效能優化,並且要有自己的安全設計。現在拿掉的成本很低,之後加回來很容易;現在帶著走,它會變成每一次安全討論都要處理的包袱。
