## A. 狀態儲存 — 兩個名字,還是三個不同的東西

| 誰 | 名字 | 內容 | 範圍 | 存活 |
|---|---|---|---|---|
| Zhexuan | `session mapping` | 佔位符標籤一致性 | 單 session | 有限 |
| Karina | `vault` | 佔位符 → 真值 | 單 session | session 結束清除 |
| **Zhexuan** | **`global context store`** | **已知實體、私密資訊** | **跨 session、跨呼叫端** | **持久** |

前兩列是同一個元件的兩個名字。第三列是全新的。

**建議:**前兩個統一叫 `vault`。`global context store` v0 不要做 —— 它持久保存而 vault 會清除、
加密與保留期限與存取控制都沒有規格、跨呼叫端共用是沒人要求的隱私問題、而且核心流程不需要它。
移到後期,並且要有自己的安全設計。

**具體問題:**如果 CEO 的助理和 CFO 的助理共用同一個 context store,CFO 那邊查一個人,
會不會拿到 CEO 這邊記錄的資訊?客戶文件裡沒有任何地方要求這件事。

**負責:**Zhexuan

## B. 信心分數歸誰、用哪一版

三個人各寫了一版,而依 `todo/TODO.md` A9 它屬於 Anmol 的領域 3。
會變成這樣是因為 Anmol 卡在硬體(D24)沒交出文件,不是三個人想搶。

同一個 span(`Harborview`,原始 0.55),三種算法三個數字:
Yudi 的校準上報 0.30、Karina 的偵測器投票比例是 0.33、Zhexuan 的 API 欄位就寫 0.55 且沒說方法。

**建議按工作流邊界三分:**

| 環節 | 誰 | 採用哪一版 |
|---|---|---|
| 產生原始分數 | Anmol(領域 3) | 他自己實作,沿用 PR #2 的訊號優先序 |
| 校準程序 | Yudi 提供、Anmol 實作 | Yudi 的 —— 最完整,而且有備案方法 |
| 選定門檻 | Karina(領域 1) | 門檻是評測的產出 |
| API 欄位 | Zhexuan(領域 4) | 承載**校準後**的分數,規格要寫明 |

每個 span 加一個 `score_method` 欄位,否則看到 0.55 分不出那是什麼。

**連帶影響:**`todo/TODO.md` B33 的交接範圍要擴大 —— 不只 Zhexuan 的 PR #2,還包含 Yudi 的校準程序。

**負責:**Anmol
