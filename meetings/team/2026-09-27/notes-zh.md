## 1. 類別清單 — 定案

**採用 Yudi 文件裡的五個等級,不另起一份。**只做兩個格式調整:

**① 把等級那一列拆成單一 id**,因為標註時一個 span 只能填一個值。

| Yudi 的等級 | 拆成 |
|---|---|
| High(個資) | `government_id` `credential` `financial_account` `medical` |
| High(商業機密) | `business_confidential`(維持一整包) |
| Medium | `person_private` `contact_personal` |
| Low | `location` `date_time` `org` `demographic` |
| Public | `person_public` `contact_public` |

**② 加一欄「能不能讓模型決定」**(Zhexuan 的貢獻)。這和低門檻不一樣:Yudi 的 High 是門檻 0.2,模型只有 0.1 把握時仍會原樣送出;標成「不能讓模型決定」則是不管幾分都不放行。**第 4 件的方案也靠這一欄。**

**改名:**`health` → `medical`。理由:Zhexuan 的 API 契約同時有 `regulated:health`(醫療資訊)和 `/healthz`(服務存活),同一份文件兩個 health。

**兩處偏離 Yudi 原文,待他確認:**
- 加了 `quantity`(金額、百分比)—— 他的五個等級沒有數字類
- `org` 統一放 Low —— 他原本「組織名」在 Low、「公開場合的公司名」在 Public,簡化後弄丟了這個區分

**一併確認的三件事:**
- 「標準鬆」的項目湊在一起要收緊(城市+性別+生日可識別 87%)
- 金額歸類靠模型判斷,不寫死規則
- `confidential_marking` 是整封信的標記,不是某個字

**已知缺口:**`business_confidential` 是五個 regulated 裡唯一偵測不到的,**需要客戶提供詞表**。

## 2. 標註要記什麼 — 定案

每個標到的東西記六件事:

| 欄位 | 值 |
|---|---|
| 位置 | 起訖字元 |
| 型態 | `電話` / `人名` / `公司`… |
| 類別 | 第 1 件清單的 id |
| **正確答案** | **一定要遮** / **遮不遮都行** / **千萬不要遮** |
| 來源 | 主管打的 / 本文 / 引用串 / 簽名檔 / 不確定 |
| 實體編號 | Sarah 與 Sarah Chen 共用一個 |

外加整封信一個欄位:`是否被標記為機密`。

**正確答案採三值,不是兩值。**第三個值是必要的 —— 有些東西遮掉會把任務弄壞(遮掉日期就無法排程、遮掉公司名就無法查詢)。這兩個情況本來就在 Karina 文件裡標紅,只是原本的格式表達不出來。

**另外拍板:`引用串` 不算「來源不明」。**引用串的來源很清楚,就是前一封信。「不確定」只留給真的分不出來的情況。否則主管的信幾乎每封都因為有引用歷史而被整封擋下。

## 3. 模型不確定時怎麼辦 — 定案

- 只留**一個**門檻,不要兩個
- 低於門檻的**照樣遮**,但標記為「不太確定」
- 那批標記**就是「遮過頭多少」的量測資料**,不必另做一套
- `PENDING_REVIEW`(人工審查)**保留在 API 規格,但這版不啟用**

**依據:**人工審查存在的前提是「遮錯代價很大」,而全遮還原的論點正是「遮錯代價很小」。代價小就不值得佔用一個人。

**連帶效果:**Yudi「不需要逐項人工審查」的研究貢獻主張保住;Zhexuan 的機制沒有被丟掉,只是先關著,客戶日後要用不必改介面。

## 4. 遮過了算不算送出去 — 未採納,帶到客戶會議

**結論:不採用方案 B。**議題保留,**帶到 2026-09-28(一)18:00 的客戶會議直接跟客戶討論。**

議程上的建議是 B(只擋含管制內容的**那一段**,不是整封信),理由是 A(整封擋)和 C(全遮照送)的差別取決於一個法律問題,而 B 在兩種答案下都成立。團隊決定不走這條。

**要留意的後果:**不採用 B,等於 A 與 C 之間<b>仍然沒有結論</b>。這代表:

- 政策閘門要擋到什麼顆粒度,**要等客戶回答之後才能定**
- 在那之前,這一段架構無法動工
- 今天對客戶的說法也不同 &mdash; 不能講「我們的設計不管你們怎麼答都能動工」,而是要把問題原樣拋回去
