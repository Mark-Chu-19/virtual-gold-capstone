## 細節

**專案範圍與議程。** Mark Chu 開場說明這是第四週的會議,團隊還有 15 週完成混合式 AI 助理的 capstone 專案(譯註:應為 11 週)。Mark 列出五段議程:架構研究、架構檢視、benchmark 比較、關於額度與沙盒的待確認問題、以及 Scope of Work 協議。

**信心評分與模型選擇的研究。** Mark 報告了信心訊號與 harness 政策的研究,指出 token 對數機率與語意熵是每次查詢近乎零成本的方法。Mark 解釋團隊避免直接問模型的信心,因為 3B 到 9B 的開源模型有 91.7% 的時間自稱信心至少 95%,造成飽和。本地模型方面,計畫以 Llama 3.1 8B 為主,另以一個 3B 參數模型處理程式與多語言查詢(譯註:應為 Qwen3 8B),先從 MMLU 子集與 GSM8K benchmark 開始。

**信心方法與 benchmark 的評估。** Alex 請 Mark 說明信心等級與 benchmark 之間的關係。Mark 解釋 benchmark 用來在採用最終信心訊號之前評估不同方法,而本地模型的信心分數則是決定 API 呼叫要走本地還是雲端的依據。

**提議的混合架構概覽。** Mark 展示了本地優先的混合架構:REST API、不做圖形介面;閘道負責政策、認證、個資偵測與遮罩;自訂的 router 與編排層;本地推論用 Hugging Face transformers。Mark 說明架構以信心分數決定是否需要升級到雲端,並以敏感度分級(譯註:原文 least-privilege classes)管制資料傳到雲端。

**架構中的敏感度與資料去識別化。** Alex 問資訊的敏感度如何判定,並建議考慮部分提示限制、輸出審查或分流路由,而不是嚴格的二元閘門。Mark 說明有一個獨立的去識別化元件,目的是在資料送到雲端 API 前移除敏感資訊;Anmol Sahu 補充團隊正在研究把資料標記為內部或機密。

**上游系統與資料管線處理。** Priya Iragavarapu 詢問餵入本地層的上下游系統。Anmol 回答高階架構設計為與情境無關;Mark 解釋機密資料可以經由資料管線處理,在送雲端前把客戶與組織的名稱或 ID 換成隨機編號,回來後在本地迴圈中還原。

**為專案選擇領域與使用情境。** Priya 建議把問題錨定在特定領域,例如零售;Mark 提議聚焦金融服務,例如信用卡、貸款、銀行帳戶,方便做合成測試。Inderpal Bhandari 接著提出一個具體的金融交易使用情境:利用公開市場資料與公司申報文件,讓交易員把交易策略留在本地,同時利用市場情報。

**實作平台與時程可行性。** Inderpal 詢問實作平台,以及專案是否能在 15 週內完成。Mark 確認聚焦於 Llama 這類開源本地模型,並自行重建 LiteLLM 作為閘道以確保資料隱私與透明(譯註:原文 LightLLM;實際決定是自寫 router,不用 LiteLLM)。Anmol 表示時程完全可行,而且用 Claude 或 Codex 這類 AI 編碼代理會加速。

**配置情境與評估指標。** Mark 提議測試三種配置:純本地、混合、純雲端,以準確率、延遲、每題成本、升級率、個資洩漏率、prompt injection 抵抗力等指標評估。Priya 問準確率怎麼衡量時,Anmol 提出建立 golden dataset 或用 LLM 當評審;Priya 則指出網路上有免費的、預先發布且附標準答案的模擬資料集。
