02 · 誰呼叫雲端提案

脫敏完之後,是我們直接送雲端,還是把乾淨文字還給他們、由他們送?

確定的部分:Aarvin 信說「我們的系統會在文字抵達 AI 助理之前自動呼叫它」;會議紀錄說我們是 intermediate layer,「before passing them to the main agent orchestration」。兩處都指向他們掌控主流程。但兩個端點的具體形狀是我提的,沒有人確認過。

選項評估
我們代送對照表完全不外流,但我們要管他們的金鑰、成本、重試、逾時
他們自己送 ✓
我們開兩個端點		/sanitize 收原文回乾淨文字,/restore 收雲端回覆回原樣
對照表也給他們我們無狀態,最單純。但對照表就是那份機密本身
怎麼說服 Aarvin「你不用把金鑰給我們,也不用為了我們改雲端供應商。我們只要兩個 HTTP 呼叫。」對工程師是減法,不是加法。
這個提案有個已知缺口未知 #2:如果 decompose 真的是指「把請求拆成公開/機密兩半」,兩個端點不夠 — 還缺一個輸出,告訴他們哪一半該送雲端、哪一半要留在本地。這個設計要等 decompose 的定義確定才能定案。

03 · 怎麼判斷要遮什麼提案

誰來決定這段字算不算機密?

確定的部分:Aarvin 要求由本地模型判斷並輸出信心分數。Yudi 的研究(已向客戶簡報)則指出情境敏感度的人類一致率只有 48%,建議把判斷範圍壓到最小。兩者都是事實;怎麼調和是我的提案。

選項評估
全部交給模型Aarvin 要的。最靈活,但有 48% 天花板、擋不住注入、講不出理由
全部靠規則不會錯,但真實信箱不可能窮舉
三關查表 +
查不到才問模型 ✓		先問「從哪來」「長得像什麼」「政策表怎麼寫」,答不出來才交給模型並附把握程度
依據五個真實信件例子跑下來的結果,詳見 sanitization-gate-options-zh.html。純查表輸在「外部來信但內容敏感」和「內部代號」;純模型輸在「信裡藏指令」,而且輸的方式是整個系統被外人接管。
怎麼說服 Aarvin不要說「你的做法不好」。說:「你要的判斷我們照做,但先讓便宜又不會錯的部分處理掉大半,模型才有餘力專心處理真正難的。」對他是減負擔,不是否定。
前提未知 #1:第一關需要對方告訴我們出處。拿不到,這一關就廢了,整個提案退化成純模型。

04 · 遮成什麼提案

判斷出「這個要遮」之後,換成什麼?

確定的部分:Yudi 的研究提出依欄位型態分開處理(識別碼假名化、數量縮放、屬性泛化、筆記丟棄),並指出泛化在多輪對話中退化最嚴重。把它對應到信件情境、以及下面那個「問對問題」的框架,是我提的。

先把問題問對

直覺會問「怎樣最安全?」— 照這個問法,答案永遠是「全部刪掉」,然後服務就沒用了。

建議的問法「雲端 AI 拿這個欄位要做什麼?」

需要指涉它 → 給假名
需要計算它 → 等比例縮放
需要知道哪一類 → 講模糊但保持為真
根本用不到 → 直接刪掉
型態例子換成換得回來?
識別碼
人名、公司、專案代號		Blue Harbor / Chen穩定假名 Project_A / Person_1可以
絕對數量
金額、股數、人數		240 萬乘一個只有我們知道的係數 → 72 萬可以
屬性
產業、職稱、地區		KRE模糊但為真 → 一檔區域銀行 ETF不行
純識別符
電話、卡號		412-555-0182直接刪掉不行
自由文字筆記主管手寫想法丟棄不行

穩定假名:同一個 session 裡 Chen 永遠是 Person_1,雲端才能前後一致地談論同一個人。

完整走一遍

① 主管原文Blue Harbor 這季預算 240 萬,比原本多 18%。幫我擬信給 Chen(412-555-0182)說明一下,抄送 Sarah。
② 送去雲端Project_A 這季預算 72 萬,比原本多 18%。幫我擬信給 Person_1 說明一下,抄送 Person_2。
③ 雲端回覆Dear Person_1,關於 Project_A 本季預算調整為 72 萬(較原規劃增加 18%)……
④ 還原後交給主管Dear Chen,關於 Blue Harbor 本季預算調整為 240 萬(較原規劃增加 18%)……

雲端全程不知道這是哪個專案、金額多少、寄給誰,但它寫得出這封信。

會踩到的坑縮放只能用在「絕對量」,不能用在「比率」。金額乘 0.3、百分比也乘 0.3 的話,只要雲端拿這兩個數字做過運算,結果就錯,而且很難發現。同理「數量」與「單價」各自乘 0.3,總價會變成 0.09 倍。

規則:同一 session 內所有絕對量共用一個係數;比率、百分比、單價一律不縮放。

還原時要檢查三件事

1雲端編出對照表裡沒有的假名(例如自己寫了 Person_7)— 換不回去,必須偵測並標記,不能默默放行
2還原必須全域一致,不能只換部分
3雲端回覆要當成不可信輸入,還原後要再掃一次 — 不能因為是我們送出去的就信任回程
否決的做法為什麼
一律 [已遮蔽]最安全也最沒用,信擬不出來
一律泛化AI 無法指涉。Yudi 研究:泛化在多輪中退化最嚴重(追問後外洩 +11.8 個百分點)
格式保留的假值AI 看不出是假的 — 可能把假電話寫進真的要寄出去的信
加密後送出AI 無法對密文做事。同態加密、安全多方計算同理(Yudi 引的評測:八種技術皆不具部署可行性)

05 · 出口怎麼把關提案

誰有權決定「這份可以送出去了」?

選項評估
模型說可以模型被騙就直接放行,沒有第二道
程式碼黑名單擋得掉列進表的,擋不掉沒想到的
程式碼白名單 ✓先由問題本身決定「這次允許放出哪些欄位」,不在名單上一律不准出去
為什麼差別在預設值:黑名單預設放行,白名單預設攔下。安全機制的預設值必須是「不」。

還有一個細節:白名單要在讀任何外部內容之前就決定好。先讀信再決定放什麼,信裡藏的指令就有機會影響那個決定。

06 · 信心分數要對什麼評分未知,不建議現在裁決

Aarvin 要信心分數。但是對什麼的信心?

我先前講錯的地方我之前說「原本那套路由已經沒了,所以信心分數應該改成對隱私判斷評分」。那是我的推測,沒有來源。實際上會議紀錄裡兩種都在:

① Aarvin 的信明確要求「本地模型做判斷並輸出信心分數」— 對隱私判斷
② 會議紀錄 p7:Anmol 提議「在回程加一層 LM 評估,對照信心門檻再送回」,Aarvin 回應方法可行、但需要人來定義正確條件 — 對答案品質

兩種都在紀錄上,沒有人裁決過。
提案明天不要急著二選一,而是問 Aarvin:「你要的信心分數,是對『這段算不算機密』的把握,還是對『這個答案可不可靠』的把握?」

這題問清楚之前,Zhexuan 的 harness 先不要動方向 — 既有的校準、ECE、AUROC 方法論兩種都用得上,不會白做。

期週做什麼要 GPU?

注意這個排程假設主線就是脫敏服務。如果未知 #3(路由還算不算數)的答案是「還算」,這張表要重排。
