1 · What this has to solve

Constraints

Four conditions that pull against each other:

ConditionSource
The local model makes the contextual judgments and outputs a confidence scoreAarvin's emailgiven
Human agreement on contextual sensitivity is 48%, so the judging surface should be as small as possibleYudi's researchgiven
The model can be fooled by instructions hidden in a message, so it cannot be the only control pointYudi's researchgiven
We may not be told where each piece of text came from — the NDA is unsigned and they are reluctant to share internal architectureSep 21 notes, p4 & p7given

The first two look contradictory; the fourth makes it worse, because every earlier proposal assumed we would get provenance. The design below runs without that assumption.

2 · The core idea

Three signals

Do not ask "should this be redacted". Split it into three independent questions, each answered by a different source.

Signal A · Type
What kind of thing is this? A phone number, an amount, a person, a project codename, or a block of free text? Decided by the content — pattern matching first, escalating only when it fails.
Signal B · Sensitivity
How confidential is it? Decided by where it came from — provenance sets a starting level, the policy table maps type to level, and the model may only raise it from there.
Signal C · Necessity
Does this particular task need it? Decided by the executive's own instruction, without reading the message at all. "Draft a reply" needs the recipient and the subject, not a phone number; "summarize this" does not even need the recipient.
Why split it this wayThe three signals fail for completely different reasons, so they do not fail together. Signal C matters most: it reads only what the executive typed, and it finishes before any message content is touched — so nothing planted in a message can influence it. That is the security foundation of the whole design.

5 · Three rules

The substance

Almost all of the value in this proposal is in these three.

Rule 1 · The ratchet Sensitivity may only be raised, never lowered.

Provenance sets a starting level (external mail = public, the executive's own draft = restricted). The model may raise it and may never lower it.

① Reading "please keep this confidential", the model can take an external message from public to restricted — fixes example 3
② A model fooled by a planted instruction can only make things safer
③ The model's errors are one-directional — only over-conservative. Over-conservative is measurable and tunable; a leak is not
Rule 2 · For unknowns, first ask whether it is a "thing" When all three tiers fail to type a span, neither drop everything nor pseudonymize everything — ask whether it is an entity that can be referred to.

ShapeHandlingWhy
Entity-like
short, recurring, referrable		pseudonymBlue Harbor → Token_1. The cloud knows it is "the thing being discussed" and can write the letter — fixes example 5
A block of prosedropReplacing a paragraph with Note_1 is the same as deleting it; the pseudonym buys nothing

e.g. an unfilled order		dropEven Order_1 discloses that such an order exists
Pseudonyms satisfy both safety and usefulness — but only for entities.
Rule 3 · Session disclosure budget Every release is charged against an allowance, and it stops at the cap.

Each request looks safe on its own; the accumulation may not be. Twenty individually harmless questions can still reconstruct the whole picture.

This matters more here than in the original research, because this is an assistant one executive uses every day: same person, same projects, same counterparties, dozens of times a day — and the cloud sees it as one continuous stream. A month of small pseudonymized fragments gives a reasonable chance of working out who Person_1 is and what Token_1 is.
What the three do togetherThey flatten the cost of being wrong.

There are normally two kinds of error: failing to redact (a leak — a disaster) and redacting too much (annoying, but safe). Rule 1 guarantees the model can only err toward safety, rule 2 keeps the default handling of uncertainty usable, and rule 3 catches what is safe per request but unsafe in aggregate.

Only the second kind of error is left, and that one is measurable and improvable. That is why we can afford to put a model in at all — not because it is accurate, but because the way it fails is safe.
Provenance of these rulesRules 1 and 3 come from Yudi's research (the one-directional ratchet, the session budget). The three-way split in rule 2 is Mark's addition — Yudi's original disposition table drops everything here, which is correct in his financial setting (his S3 holds unfilled orders and strategy notes, neither of which a pseudonym can save). The email setting adds entities like project codenames, where pseudonyms do work. Not yet reviewed with Yudi.

6 · Disposition matrix

How the signals combine

Signal C decides which types may leave at all, then it crosses with sensitivity.

Sensitivity \ NecessityRequiredHelpfulNot needed
S1 Publicsend as-issend as-isdrop
S2 Confidentialhandle by type, then sendsend only if budget allowsdrop
S3 Restrictedby type: entity → pseudonym; prose or existence-is-the-secret → dropdropdrop
Unknowntreat as S3drop
Why S3 × helpful = drop"Helpful" is defined as the task still succeeds without it, just slightly worse.

S3 means disclosure causes direct harm. Trading "slightly better output" for "one more exposure of the most restricted material" is a bad deal.

The S3 row accepts "unavoidable". It does not accept "nicer".
Look at the whole right-hand columnIf this task does not use it, it is dropped however confidential it is — no judgment required at all. That column removes more than people expect: summarizing a message needs no phone number, no account number, no calendar. However wrong the sensitivity call is, this column is unaffected.

8 · What if we get no provenance

NDA unsigned

The NDA addendum is unsigned and they are reluctant to share internal architecture (Sep 21 notes, p4). Telling us "this came from the contact list" is itself a statement about how they store data — so the provenance field may not be available.

What degrades
Signal B loses its starting level → everything is treated as S3. The ratchet already sits at the top, so the model-endorsement step becomes moot.
Why it still works
Because of rule 2. S3 + required = pseudonym, not deletion. So in degraded mode almost everything is pseudonymized but the service still functions — the cloud receives a message full of Person_1 and Token_3 and can still draft a reply, which is then fully restored.
What is lost
Public material that could have been sent as-is (a quoted article, a public quote) is pseudonymized too, so the cloud understands less. That is measurable — it is the usability gap between "with provenance" and "without", and that number is exactly the argument for asking.
So do not ask "can you give us provenance"Instead: we define an optional source field in the API spec and list the values we accept. They leave it empty for now and the service degrades automatically; once the NDA lands they populate it, with no interface change.

Also worth separating coarse provenance ("this span is user input / this span is document content") from fine provenance ("this came from table 7 of contacts_db"). We only need the coarse kind, and that is a very ordinary API pattern rather than an architecture disclosure — so the NDA may not actually block it. Worth asking directly.

The Sep 21 next-steps assign the endpoint spec to Alex and Aarvin, so proposing the field definition helps them rather than asking them for something.

9 · Where the model sits, and where the score sits

Answering Aarvin

Aarvin asked for "the local model makes these judgments and outputs a confidence score". This design does exactly that, in two specific places.

Where the model appearsWhat it doesConsequence if wrong
Signal A, third tierTypes a span that pattern matching and NER could notWrong swap applied → less usable, no leak
Signal B, endorsementReads free text and decides whether to raise sensitivityMissed → level stays; over-raised → over-conservative. Because of the ratchet, neither leaks
Where the confidence score is usedOn the signal B endorsement. The model says "this reads as confidential, confidence 0.85" and a threshold decides whether to raise.

Low confidence pushes upward, not sideways. Uncertain means more conservative — which gives the score a concrete downstream use rather than being a number nobody consumes.

And the score appears only where there is genuine uncertainty (free text), so the output is not full of meaningless "1.0, because the pattern matched" entries.
How to put it to Aarvin"The model judges in two places and the confidence score drives one of them. We have not removed anything you asked for — we have arranged it so that when the model is wrong, it cannot cause a leak. The worst it can do is make us over-conservative, and we can measure and tune that."

Why this splitEvery phase ends with a working service, not a half-built one. Phase 1 has no ML, no GPU, no error rate, and does not wait on the sandbox (B15 has been with the client for two weeks). Phase 2's value can be measured against phase 1 as the control — and that comparison is itself the midpoint result.

11 · Weaknesses of this proposal

Stated plainly
WeaknessSeverity
Cross-request state is unsolved. Two problems that are really one: (a) whether a ratchet endorsement persists across turns — repeated endorsement within one conversation could eventually block everything; (b) how the rule-3 budget is replenished — never, and the assistant stalls each day; too fast, and there is effectively no budgetNo answer to either. Yudi's research states outright that budget replenishment is unsolved, so this is not merely my gap
Signal C depends on correct task classification. Misclassify "summarize" as "draft" and the allowlist opens wronglyReal risk. Mitigation: fall to the strictest row on failure. But the classifier is itself a model
The policy table has to be written by a person and signed by the client. Example 3 showed what a badly written table costsUnavoidable, and it will hold up the schedule. Start early
Heavy pseudonymization degrades the cloud's comprehension, especially in degraded modeMeasurable; it is the argument for provenance
"Unrecognized entity" and "block of free text" must be separable. Pseudonymizing a short entity works; pseudonymizing a paragraph is deletionImplementation detail, but it decides how much rule 2 actually buys
The biggest single unknown is still the same oneSignal B's starting level comes from provenance. Whether the API contract carries that field has to be confirmed first. Without it this proposal still runs (section 8), but nobody currently knows how much usability that costs — which is precisely what phase 3 is meant to measure.
